# Twinly 保存・性能・信頼性の改善

結論：Firebaseの全面撤去より、全記録を一文書に詰めた保存構造の解消と、画面からの保存処理分離を優先する。既存アカウントの自動データ移行は行わない。今回の変更は既存形式と新形式を読み書きできる互換リリースである。

## 確認した問題と対応

| 優先度 | 実装で確認した問題 | 今回の対応 |
| --- | --- | --- |
| 最優先 | `families/{id}/app/state.app.events` に全履歴を格納し、毎回全件をトランザクションで読み書き | 記録単位の `events/{id}` と小さな設定文書に分離できるアダプターを追加。既存形式は維持、新規作成はv2 |
| 最優先 | 追加以外の未同期変更が残らず、失敗も画面に出ない | 家族・ユーザー別の永続キュー。追加・編集・削除・設定を保存してから画面反映。順番に再送し、処理済みIDで重複適用を防止 |
| 最優先 | 家族復元の通信失敗を未登録と扱う | 登録が必要な状態と取得失敗を分離。古いログイン処理の応答が新しいユーザーの状態を上書きしないよう世代管理 |
| 高 | 通常画面にも全履歴が必要 | v2では過去30日＋それ以前の種類別最新記録だけを購読。履歴・統計・設定を開いた場合や古い日付の表示時に全履歴を読み込む |
| 高 | おむつ記録と在庫更新が別の保存。Undoで在庫が戻らない | 保存を一操作に統合。消費したサイズと枚数を記録し、削除・Undoで復元。通信再送と最終1枚の同時消費にも対応 |
| 高 | 初回JavaScriptにグラフが含まれる | グラフ・履歴・レポート・週間表示を遅延読み込み |
| 高 | CIがインデックス変更を対象にせず、浅い履歴や失敗後の差分判定でデプロイ漏れが起こり得る | 最後に成功したデプロイとの差分で判定。手動実行・設定変更は全対象。インデックスも対象。実行途中の中断を防止 |
| 中 | ログイン時に通知設定を毎回既定値で上書き | 初回だけ作成し、既存の通知設定を保持 |
| 中 | アプリシェルが古いまま残り、認証ページやHTML応答までキャッシュされ得る | 成功したナビゲーションでシェル更新。認証経路を除外し、静的ファイルのみ保存 |
| 中 | インポートで型検証せず成功扱い。Rechartsの古いクリックイベント型 | インポート検証と置換確認、現在の依存バージョンに合わせた型修正 |

## 変更後の境界

- `src/data/app-repository.ts`: Firebase型を含まない保存契約、差分作成、競合検知。
- `src/data/firestore-app-repository.ts`: Firebaseへの読み書き、v1/v2互換、期間指定、ページ単位エクスポート。
- `src/data/app-store.ts`: 永続キュー、楽観的表示、再試行、バックアップ、競合時の停止。
- `src/lib/event-mutations.ts`: 記録と在庫の業務処理。
- `functions/app-storage.js`: Watch・通知の新旧保存形式への対応。

別のDBへ移す場合はまず保存アダプターを置き換える。認証・通知・Watchは引き続きFirebaseに接続しており、全面的な脱Firebaseを完了した変更ではない。

## 効果と測定範囲

- 同じ依存関係でのビルド比較：初回JSは1,500.35KB（gzip 418.41KB）から約1,125KB（gzip約308KB）。初回JS転送量は圧縮後で約26%減。後から開くグラフ等の転送量は別途発生する。
- v2で通常のミルク1件追加は、対象イベントと処理済みIDの2文書を書き込む。設定や他の育児記録は再送しない。トランザクションで設定・処理済みID・対象イベントを読む。
- 全履歴が10,000件あっても、1件追加の変更データが500文字未満に収まることをテストした。これは生成差分の検証であり、本番DBのレイテンシ測定ではない。
- 読み書き文書数は旧方式より増える場合がある。転送量・競合・サイズ上限を改善する設計であり、Firebase料金の削減を断定しない。
- Firebase構成ファイルのDBロケーションは `nam5`、Functionsは `asia-northeast1`。実環境の配置確認と計測が必要。既存DBの場所はこの変更では移していない。

## 検証

- 型チェック、プロダクションビルド。
- フロントの保存契約・オフライン再開・競合・家族セッション・既存集計・音声解釈の対象テスト。
- 501件の移行を途中で止めて再開し、元データ・バックアップ・全イベントの一致を確認する管理用テスト。
- 実Firebaseエミュレーターは起動時のネットワーク制約で利用できず、Security Rulesの実行検証、実認証、実端末間同期、本番遅延測定は未実施。テスト用メモリ実装の検証と区別する。

## 本番への反映手順

1. この互換版のRules・インデックス・全Functions・Hostingを反映し、インデックスが使用可能になったことを確認する。コードのデプロイだけでは既存家族の保存形式は変わらない。
2. 実アカウントで既存記録・ログイン・追加／編集／Undo・Watch・通知を確認する。旧端末の未同期を完了し、JSONバックアップを取得する。
3. 対象の家族IDを `users/{uid}.activeFamilyId` で確定する。ユーザーIDを家族IDと決めつけない。
4. 管理権限のある環境でドライランする。スクリプトはApplication Default Credentialsを利用し、鍵をリポジトリに保存しない。

```bash
node functions/scripts/migrate-event-storage.js twinly-prod FAMILY_ID
node functions/scripts/migrate-event-storage.js twinly-prod FAMILY_ID --apply
```

5. 移行開始時、元文書を `families/{id}/storageBackups/before-events-v2` にそのまま保存し、旧形式への書き込みをロックする。安定したIDで400件ずつ転送し、全件を比較してからv2へ切り替える。失敗時は元文書を残し、同じコマンドで再開する。
6. 端末を再読み込みし、件数・集計・在庫・同期・全件エクスポートを確認する。v2で新しい記録が生じた後に古いバックアップをそのまま戻すと新しい記録が失われるため、単純なロールバックは行わない。

## 残る制限と次の判断

- v2の一操作は450イベントまで。大量の一括インポート・全削除は部分成功による欠損を避けるため、受理前に拒否する。一般公開前に専用の再開可能な一括処理を追加する必要がある。
- 履歴・統計・設定を開くと全履歴を購読する。通常画面の負荷は抑えるが、長年分の分析画面は期間指定・集計保存へ拡張する余地がある。
- 未同期キューはlocalStorageを利用する。容量不足時は変更を受理せず通知する。IndexedDBキューと端末ごとの安全なサインアウト方針は次段階。
- 処理済みIDは安全な再送のため期限を設けていない。利用規模が増えた場合の保持・掃除方針が必要。
- 同じイベント・設定の同時編集は自動上書きせず停止する。未同期内容の書き出し、再試行、利用者による未同期取消が可能。
- 一般公開に向けては、アカウント／家族の退会とデータ削除、招待の運用、監視・課金上限、実DB負荷試験、端末間の受入確認が別途必要。公開準備がすべて完了したとは扱わない。

設計判断の参考：Firebase公式の[ベストプラクティス](https://firebase.google.com/docs/firestore/best-practices)と[オフライン保存](https://firebase.google.com/docs/firestore/manage-data/enable-offline)。単一文書の集中更新を避け、既存の同期機能を活かして段階的に改善する。
